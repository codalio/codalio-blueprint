# Productivity Metrics — Lens Prompts

Three independent lenses over the same collector JSON (see `SKILL.md` step 2).
Each lens receives: the collector JSON, the user's question, and the window.
Every lens uses these shared rules:

- Only PRs with `in_window: true` and `is_bot: false` count toward figures,
  unless the lens says otherwise (the impact lens also reads PRs outside the
  window to build its "before" period).
- Report medians, not means — PR cycle times are heavily skewed. Add p90 when
  there are at least 10 data points.
- Every figure states its sample size (`n`) and window.
- Hours under 48 read better as hours; above that, convert to days.

## Lens 1 — Team Delivery

**Task:** Describe how work flows from opened PR to release in this window.

Cover:
- **Throughput** — merged PRs in window, merged PRs per week (`summary`).
- **Cycle time** — PR open to merge, median and p90 (`summary.cycle_hours`).
- **Review latency** — PR open to first review by someone other than the
  author (`summary.first_review_hours`). Note how many PRs got no review at
  all — on small teams that is often the real story.
- **PR size** — median lines changed (`summary.size_lines`). Large PRs usually
  explain long cycle times; say whether they do here.
- **Release frequency** — releases in window, and average days between them.
- **Change-failure proxy** — reverts in window, plus `fix` PRs that touched a
  file changed by a `feat` PR in the preceding 14 days. Label it a proxy.
- **Work mix** — count of in-window PRs by conventional-commit `type`.

**Output contract:** Return a short markdown section per item above, each
with figures and one sentence of interpretation. End with the single biggest
constraint on delivery the data points to. No preamble.

## Lens 2 — Blueprint Impact

**Task:** Determine whether and how the codalio-blueprint skills are being
used in this repository, and whether delivery looks different since.

Cover:
- **Adoption** — from `skill_artifacts`: which skills produced committed
  files, when each first appeared (`committed_at`, falling back to
  `marker_date`), and the file paths. If the list is empty, say no committed
  skill output was found and stop the comparison there — the skills may still
  be in use without their output being committed, so say that too.
- **Before / after** — split all non-bot merged PRs (in or out of window) at
  the first adoption date. Compare median cycle time, review latency,
  merged PRs per week, and PR size across the two periods, with `n` for each
  side. Use Lens 1's definitions.
- **Traceability** — PRs whose `files` touch a skill artifact, or that came
  after an artifact and implement what it describes (judge from titles).
- **Honest read** — one paragraph: what changed, what else changed at the
  same time (team size, project phase, repo age), and why the comparison
  cannot establish cause. Small samples on either side must be named.

**Output contract:** Return these four parts as markdown. No preamble.

## Lens 3 — Individual Developer

**Task:** Give the subject developer an honest picture of their own work in
the window, read against the team baseline.

The subject is `summary.individual.subject` — the invoking user unless the
person asking named someone else explicitly — and every account in
`summary.individual.accounts`. If `identity_groups` merged accounts for the
subject, say which accounts were merged and on what evidence before giving
any figure. Never list, rank, or compare other named individuals.

If the subject authored nearly all human PRs, the team baseline is mostly
the subject's own work — say so instead of presenting it as a comparison.

Cover:
- **Shipped** — merged PRs, grouped by type, with titles of the notable ones.
- **Flow** — own median cycle time versus team median; own PR size versus
  team median.
- **Collaboration** — reviews given on other people's PRs; how many of the
  subject's own PRs merged with no review by anyone else.
- **Rhythm** — active days (days with a merged PR) across the window.
- **One observation worth acting on** — framed as a suggestion for the
  subject, not a judgment (e.g. "most PRs merge without a second reviewer").

**Output contract:** Return these five parts as markdown. Volume figures
always sit next to a flow or collaboration figure. No preamble.

## Report Template

```markdown
# <Repo> — Productivity Report

> Generated by the productivity-metrics skill on <date>. Review and edit before treating this as final.

## 1. Scope & Data Window
<repo, window, data source (gh or git-only), PRs counted, bots excluded>

## 2. Team Delivery
## 3. Blueprint Impact
## 4. Individual — <subject>
## 5. Caveats & Data Gaps
## 6. Suggested Next Measurements
```

Section 5 collects every small-sample warning, unavailable metric, and
causation caveat in one place. Section 6 names what would make the next
report more reliable (e.g. "enable required reviews so review latency exists").
