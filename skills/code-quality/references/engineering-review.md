# Code Quality — Engineering Review

The code-read review the code-quality skill runs after measurement (see
`SKILL.md` step 12). Tools count what they can see; this review scores what
only a reader catches: design flaws, logic bugs, and missing controls. It
complements the measured scorecard and never replaces or alters it.

## Rules

- **Score the scope assessed.** For a change or commit range, score the
  changed code and the paths it touches, and label any defect that predates
  the change as pre-existing, so old debt never reads as the change's own.
- **Read, don't guess.** Read the models, controllers or handlers,
  policies, routes, schema, and frontend entry points before scoring. A
  category whose code was not read is "not scored", never a number.
- **Every score cites evidence.** Each score names the files and lines that
  justify it, both strengths and defects. A score with no citation is not
  reported.
- **Score against the anchors below**, not against an impression:
  - 1–3 **weak**: the category's basic control is missing or broken in a
    reachable path.
  - 4–6 **mixed**: the right approach exists but has a real defect or gap.
  - 7–10 **solid**: the approach is sound end to end; 9–10 also needs tests
    or tooling that keep it that way.
- **Caps.** An exploitable defect (a reachable path that leaks data or
  bypasses authorization) puts the category whose control it breaks at 1–3,
  per the anchors, and caps every other category it touches at 4 until fixed.
- **Verify before scoring.** Before calling a defect exploitable, trace the
  path from a request to the data and confirm the state it depends on is
  reachable.
- **Same bar for every author.** Generated and hand-written code are scored
  the same way.

## Categories

| # | Category | What to check |
|---|---|---|
| 1 | Security | Cross-origin policy (any origin allowed together with credentials); where auth tokens live on the client (script-readable storage vs. httpOnly cookies); secrets in code or in the repository; helpers that **fail open**, i.e. return everything when a lookup is empty or an error occurs. For a full authorization review, use the secure-coding skill. |
| 2 | Tenancy & data isolation | Single- or multi-tenant by design, and whether that matches the product; every query scoped to the current tenant; behavior when a user has no tenant or membership; whether one tenant's records are reachable through relations, nested fields, or enumeration. |
| 3 | Permission granularity | Authorization checked per route or action, not only "signed in"; role-aware rules; field-level visibility and editability; ownership checks on state-changing actions (approve, delete, assign). |
| 4 | Code quality | Business-logic correctness on the main flows; hard-coded values standing in for real ones; money held in floating point; features that look implemented but are stubbed; idiomatic, consistent use of the framework. |
| 5 | Maintainability | Clear layering (models, policies, controllers or handlers, UI); repository hygiene (no committed `.env`, build output, dependency folders, or generated reports); architecture decisions written down; one place per rule. |
| 6 | Test coverage | Whether automated tests exist for the backend and the frontend, what they exercise, and how much they cover. Use the measured coverage and pass rate from the scorecard where available. |
| 7 | Frontend engineering | A consistent component system; form validation; a typed API layer instead of untyped responses; an error boundary or equivalent; loading and error states. |
| 8 | API / data-layer design | Identifiers and sequence numbers generated by the database, not by counting rows (a race under concurrency); transactions and locking where writes must agree; centralized error handling returning structured errors, not framework error pages; input validation on every endpoint; one contract the client and server are built from. |

## Overall score and verdict

- **Overall** = mean of the scored categories, rounded to the nearest 0.5.
  If any category is not scored, say so beside the overall.
- **Engineering verdict** — one or two sentences on the experience level the
  code reads like, and why, based on the scores:
  - below 4: **junior** — basics missing across several categories.
  - 4–6: **mid-level** — sound instincts with serious gaps.
  - 6.5–8: **senior** — consistent craft; gaps are specific and fixable.
  - above 8: **staff** — strong across the board, with guardrails.

  When craft and discipline diverge (for example, strong typing but no
  authorization or tests), say so rather than averaging the difference away.

## Projected if fixed

Optional. For the top defects only, rescore assuming each named fix ships.
List each fix, every category it moves (old → new), and the new overall.
Never project a fix that has not been described concretely.

## Comparing two codebases

Score both with the same reader, the same rules, and the same anchors, in
side-by-side columns. End with a bottom line: which is safer to ship now,
why, and what each needs first.
