# Architecture Evaluation

## Overview

Assess whether an existing codebase's architecture can support a specific set
of stated requirements (a new scale target, a compliance need, a must-
integrate-with system, a new business/contract the codebase needs to win) —
and name the tech debt and risks standing in the way. This is an evaluation
of *this specific codebase against these specific requirements*, not a
generic best-practices audit.

**Announce at start:** "I'm using the arch-evaluation skill to assess your codebase against these requirements."

## Process Flow

1. **Gather the requirements.** Ask what this evaluation is for: what new
   scale, compliance need, integration, or business requirement does the
   codebase need to support? If the user has a PRD (check `docs/prd/`),
   read it for context, but the requirements driving *this* evaluation must
   come from the user directly — don't assume a PRD's original scope is
   still the bar.
2. **Clarifying questions.** Ask one at a time. Cover: what's the actual
   decision this evaluation feeds (a go/no-go, a refactor-vs-rewrite call,
   a scoping estimate)? Any hard deadline? Any part of the codebase already
   known to be a problem area?
3. **Explore the codebase.** Read enough of the actual code and structure to
   ground every claim — directory layout, core data model/schema, main
   integration points, test coverage, how the current architecture handles
   the load/pattern closest to the new requirement. Don't evaluate from the
   README or file names alone.
4. **Current architecture summary.** Plain-language description of what's
   actually there — not idealized, what's actually built.
5. **Gap analysis.** For each stated requirement, does the current
   architecture support it, partially support it, or not at all? Point to
   the specific code/pattern responsible for each gap, not a vague concern.
6. **Tech debt & risks, ranked.** 3-7 items, ranked by how much they block
   the stated requirements specifically — not a general debt inventory.
7. **Recommendation.** Build-on, refactor, or rewrite — for each requirement
   gap, not one blanket verdict. State the reasoning, not just the label.
8. **Write the doc** to
   `docs/arch-eval/YYYY-MM-DD-<project-slug>-arch-evaluation.md` in the
   user's project (create `docs/arch-eval/` if it doesn't exist).
9. **Self-review.** Check every claim traces to something actually read in
   the codebase, not assumed. Flag anywhere confidence is low because a part
   of the codebase wasn't explored.
10. **User review gate.** Point the user to the file, ask them to review
    before treating it as final. Wait for their response.

## Output Template

```markdown
# <Project Name> — Architecture Evaluation

> Generated by the arch-evaluation skill on <date>. Review and edit before treating this as final.

## 1. Requirements Being Evaluated Against
## 2. Current Architecture Summary
## 3. Gap Analysis (per requirement)
## 4. Tech Debt & Risks (ranked)
## 5. Recommendation (per requirement)
## 6. Open Questions / Areas Not Explored
```
