# PRD Builder — Lens Prompts

Three independent lenses, run either as concurrent dispatched sub-tasks or
sequentially inline (see `SKILL.md` §Running the Three Lenses). Each ends with
an explicit output contract so whatever runs it — a dispatched subagent or the
model running inline — knows exactly what to return.

Every lens receives the same input: the idea as described by the user, plus
the answers gathered during clarifying questions. Nothing else.

## Lens 1 — Product & Scope

**Task:** Given the idea and clarifying answers below, work out the product
shape and its minimum viable scope.

Cover:
- **Elevator pitch** — one sentence: "For [target user] who [problem], [product
  name] is a [category] that [key benefit], unlike [alternative]."
- **Problem statement** — 2-3 sentences on the problem being solved and why it
  matters now.
- **Target user** — 3-5 bullets describing who this is for. Be specific
  (role, context, current workaround) rather than generic ("busy professionals").
- **User stories** — 5-10 stories, each "As a [user], I want [capability] so
  that [benefit]." Cover the core flow, not edge cases.
- **MVP checklist** — every user story sorted into Now (must ship v1), Next
  (soon after), or Later (explicitly deferred). Every Now item should trace
  back to a user story above.

**Output contract:** Return only these five sections, in this order, as
markdown. No preamble, no meta-commentary about the process.

## Lens 2 — Architecture & Data (lite)

**Task:** Given the idea and clarifying answers below, sketch the minimum data
shape and flag technical risk — not a full architecture evaluation.

Cover:
- **Core entities** — 3-8 entities, one line each (name + what it represents).
- **Relationships** — plain-language description of how the entities connect
  (e.g. "a User has many Orders; an Order belongs to one Product"). Not an ERD,
  not a schema.
- **Key technical risks/decisions** — 3-5 bullets: things that could bite this
  project technically (a hard integration, a scaling assumption, a
  build-vs-buy call) and, where there's an obvious default, what to do about it.

**Output contract:** Return only these three sections, in this order, as
markdown. Explicitly note in your response that this is a lite pass, not a
full architecture evaluation. No preamble, no meta-commentary about the process.

## Lens 3 — GTM (lite)

**Task:** Given the idea and clarifying answers below, sketch how this reaches
its first users — not a full go-to-market plan.

Cover:
- **Positioning** — one sentence: "[Product] helps [target market] [achieve
  outcome] by [mechanism]."
- **Target market / early adopter** — who buys or adopts first, and why they'd
  feel the problem more acutely than the broader target user described above.
- **GTM angle + one early proof point** — the single most plausible channel or
  motion to reach the early adopter, plus one concrete, checkable signal that
  would prove it's working (a number, an action, a milestone).

**Output contract:** Return only these three sections, in this order, as
markdown. Explicitly note in your response that this is a lite pass, not a
full GTM plan. No preamble, no meta-commentary about the process.

## Output Template

The synthesis step (SKILL.md step 4) merges all three lens outputs into this
template and writes it to `docs/prd/YYYY-MM-DD-<project-slug>-prd.md`:

```markdown
# <Project Name> — Product Requirements Document

> Generated by the prd-builder skill on <date>. Review and edit before treating this as final.

## 1. Summary
## 2. Target User
## 3. User Stories
## 4. MVP Scope (Now / Next / Later)
## 5. Data & Architecture Overview (lite)
## 6. Go-to-Market (lite)
## 7. Open Questions
## 8. Appendix: Assumptions
```

Sections 7-8 exist so the self-review step (SKILL.md step 6) has somewhere to
put unresolved items instead of silently guessing.
