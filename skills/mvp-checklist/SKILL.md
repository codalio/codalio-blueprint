# MVP Checklist

## Overview

Turn a product idea (or an already-written PRD) into a rigorous MVP scope: not
just what's in v1, but what's explicitly cut and why, and what "done" means
for v1 so scope can't quietly creep. This is deeper than the lite MVP section
inside `prd-builder` — use this when the user needs to actually defend a v1
scope decision, not just sketch one.

**Announce at start:** "I'm using the mvp-checklist skill to scope your MVP."

## Process Flow

1. **Gather context.** If the user has an existing PRD (check `docs/prd/` in
   their project first), read it and reuse its target user, problem, and user
   stories rather than re-asking. Otherwise ask for the idea and target user
   directly, one open question.
2. **Clarifying questions.** Ask one at a time. Cover: timeline/deadline
   pressure, team size, what "launch" means for this project (paying
   customers? internal pilot? public beta?), and any hard constraint that
   caps scope (budget, a must-hit date, a single-person team).
3. **List every candidate feature.** Pull from the PRD's user stories if one
   exists, or elicit them directly. Don't filter yet — get the full
   candidate list first so cuts are visible decisions, not silent omissions.
4. **Score each feature.** For each candidate, judge: does the core value
   proposition work without it? Cheap or expensive to build? Does removing it
   break a user story that's otherwise in v1? Use these judgments, not gut
   feel alone, to sort into Now/Next/Later.
5. **Write the explicit cut list.** Every feature sorted Next or Later gets
   one line: what it is and why it's not in v1. This is the section users
   skip when scoping casually — don't skip it here.
6. **Define v1 done-criteria.** 3-5 concrete, checkable conditions that mean
   v1 is complete and shippable (not "feels done" — checkable facts: "a user
   can sign up, create X, and see Y without support intervention").
7. **Write the doc** to `docs/mvp/YYYY-MM-DD-<project-slug>-mvp-checklist.md`
   in the user's project (create `docs/mvp/` if it doesn't exist).
8. **Self-review.** Check every Now item traces to a real user need, every
   cut has a stated reason, done-criteria are actually checkable (not vague).
9. **User review gate.** Point the user to the file, ask them to review
   before treating scope as final. Wait for their response.

## Output Template

```markdown
# <Project Name> — MVP Checklist

> Generated by the mvp-checklist skill on <date>. Review and edit before treating this as final.

## 1. Context
## 2. Now (v1 scope)
## 3. Next
## 4. Later
## 5. Explicit Cut List (what's out and why)
## 6. V1 Done-Criteria
## 7. Open Questions
```
