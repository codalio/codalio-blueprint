# ToolShare — Product Requirements Document

> Generated by the prd-builder skill on 2026-08-06. Review and edit before treating this as final.

## 1. Summary

For neighbors who own tools they rarely use but can't justify buying more of,
ToolShare is a neighborhood tool-lending app that lets people list, find, and
borrow tools from people nearby, unlike general marketplace apps that aren't
built for short-term, trust-based lending between neighbors.

Most homeowners own a handful of power tools they use a few times a year, and
buying a new one for a one-off job is wasteful when three houses down already
owns it. ToolShare makes it easy to find that tool nearby and borrow it
directly, without a general marketplace's friction of shipping, payment
processing, or dealing with strangers outside the neighborhood.

## 2. Target User

- Homeowners in a defined neighborhood or building complex who own tools they use infrequently
- Renters and new homeowners who need a tool for a single project and don't want to buy one
- DIY hobbyists doing seasonal projects (yard work, home repair) who need tools outside their existing set
- Existing informal tool-lenders (the "the guy on the block with the ladder") who want lending requests to stop landing only on them
- Neighborhood or building associations looking for a low-cost shared-resource perk to offer residents

## 3. User Stories

- As a tool owner, I want to list a tool with a photo and short description so that neighbors can find it.
- As a borrower, I want to search for a tool by name or category so that I can quickly find what I need nearby.
- As a borrower, I want to see a tool's availability before requesting it so that I don't waste time on unavailable items.
- As a tool owner, I want to approve or decline a borrow request so that I control who takes my tools.
- As a borrower, I want to message the owner directly so that we can agree on pickup time and place.
- As a tool owner, I want to mark a tool as returned so that it shows available again.
- As a user, I want to see a simple trust signal (e.g. verified address, past successful loans) on someone's profile so that I feel safe lending or borrowing.
- As a tool owner, I want to set a lending radius or limit lending to my building/neighborhood so that I only lend to people nearby.
- As a borrower, I want to rate a loan after it's returned so that the community can trust future listings.
- As a user, I want a notification when a request, approval, or return happens so that I don't have to check the app constantly.

## 4. MVP Scope (Now / Next / Later)

**Now**
- List a tool (photo, name, category, description)
- Search/browse tools by neighborhood
- Request to borrow + owner approve/decline
- Direct messaging between owner and borrower
- Mark tool as returned

**Next**
- Ratings/reviews after a completed loan
- Lending radius / neighborhood scoping controls
- Push notifications for requests, approvals, returns

**Later**
- Verified-identity trust badges
- Waitlists for popular tools
- Optional deposit/damage-protection flow

## 5. Data & Architecture Overview (lite)

> Lite pass — not a full architecture evaluation.

**Core entities**
- **User** — a person with a profile, address/neighborhood, and trust signals
- **Tool** — an item listed by a User, with category, photos, and availability status
- **Loan** — a request-to-return record linking a Tool, a borrower User, and an owner User
- **Message** — a chat message tied to a Loan or a pre-request conversation
- **Neighborhood** — a geographic grouping used to scope search and lending radius
- **Rating** — a post-loan review tied to a completed Loan

**Relationships**
A User belongs to one or more Neighborhoods. A User owns many Tools. A Tool
has many Loans over its lifetime, but at most one active Loan at a time. A
Loan links exactly one Tool, one borrower User, and one owner User, and has
many Messages. A completed Loan can have one Rating from each side.

**Key technical risks/decisions**
- Location/neighborhood scoping needs a real geo boundary source (not just a text field) or search results won't respect "nearby" reliably — use a mapping/geocoding API rather than hand-rolled radius math.
- Trust/safety (who can see whose address, how disputes get handled) is a product-risk as much as a technical one — needs a policy decision before the profile/visibility schema is finalized.
- Real-time messaging can start as simple polling; don't build websocket infrastructure for MVP unless message volume in early testing proves it's needed.
- Availability state on a Tool needs to be the single source of truth Loan requests check against, to avoid double-booking the same tool.

## 6. Go-to-Market (lite)

> Lite pass — not a full GTM plan.

ToolShare helps neighbors in the same community avoid buying tools they'll
rarely use again by making it fast to borrow from someone nearby instead.

**Target market / early adopter:** residents of a single well-defined
neighborhood or apartment/condo complex with an existing community channel
(a listserv, a Facebook group, an HOA newsletter) — they already have a way
to hear about it and a built-in reason to trust their immediate neighbors.

**GTM angle + proof point:** launch in one neighborhood via its existing
community channel rather than a general app-store listing, and recruit the
neighborhood's known informal tool-lenders as the first listings to seed
supply. Proof point: 10 completed loans within the first neighborhood in the
first 60 days.

## 7. Open Questions

- What happens if a tool is damaged or not returned — is a deposit/protection flow required for MVP or genuinely deferrable to Later?
- Should a Neighborhood be self-declared by the user or verified against an address?
- Is cross-neighborhood borrowing ever allowed, or is it strictly scoped to one's own neighborhood for MVP?

## 8. Appendix: Assumptions

- Assumes an initial launch targets one neighborhood at a time rather than a broad multi-city rollout.
- Assumes users are willing to share an approximate address/neighborhood for the app to function — full anonymity is out of scope.
- Assumes no payment processing is required for MVP (lending is free/favor-based, not a paid rental marketplace).
